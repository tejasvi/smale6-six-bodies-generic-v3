# F2: Proposition 4.5 (the cells) in Lean 4

Proposition 4.5: the enumeration lists 91,273 cells of the representatives of the 191 classes, in 69 classes, and
every nonpositive cell of a representative is in the list. Its proof is a depth-first search (insertion of the
bodies into the two trees, linear programs with the relaxation of ℓ(x) ≤ 0, then the argmin sets of the fourteen
base identities), in 384 parts per class, in which every prune by a linear program is certified by Lemma 4.6.

## What is checked

The library `L6F2` is a replica, in compiled Lean, of the engine's certified search (`types/treplay.py`,
`enumerate_cells`, tag generic-v1, options `--mode le --base --split 3 --nparts 384`):

* `L6F2/Tree.lean`: the trees of `tengine.Tree`, with the insertion orders of its three dictionaries, so that the
  insertions (`options`) are listed in the engine's order and the internal nodes get the engine's numbers;
* `L6F2/Search.lean`: `order_bodies`, `base_lp` (every row times 2), `threshold_row` (mode `le`), the base
  identities of `texact.identities`, `forced_rows`, `exact_argmins`, `cells_below`, `enumerate_cells` with the
  counter split at depth 3. Every linear program is decided by `decideLP`: the floating-point simplex of
  `L6Common/LP.lean` proposes, and a program is discarded only if `Farkas.check` (the hypotheses of Lemma 4.6)
  accepts the proposed certificate for its rows; a float prune without an accepted certificate is kept and counted
  as a failure;
* `L6F2/Point.lean`: for every cell written, an exact rational point (heights and `s`, from the floating-point basis
  of the dual program by integer elimination) that satisfies every row of the cell, with `s > 0`, and the row
  `ℓ(x) ≤ 0`;
* `L6F2/Check.lean`: `checkChunk text c` runs the parts of a chunk (consecutive parts in the byte order of their file
  names `p<part>.jsonl`, which is the order of the engine's concatenation `cells.jsonl`) and checks that the cells it
  writes are, in order, byte for byte, the beginnings (up to the key `"x"`) of the stored lines `c.off, c.off+1, …`
  of `data/cells/c<k>.jsonl`; that it writes exactly `c.cells` cells; that no linear program failed; that every cell
  has an exact point (above); and that the numbers of linear programs and of prunes, in total and part by part, are
  those of the engine's run (`data/cells/parts.tsv`, from the `p<part>.jsonl.replay.json` counters). `tilingOk text
  cs k` checks that the chunks of class `k` cover the 384 parts once, in that order, with consecutive offsets ending
  at the number of lines of the stored list;
* `L6F2/Trees.lean`: the insertions without pruning.

The stored floating-point fields of each line (`x`, `hz`, `hw`, `slack`, `sumx`) are not compared.

**Meaning, with Lemma 4.6.** For each of the 191 classes, the Lean search, run on its 384 parts, writes exactly the
stored lines of the class, in the engine's order; each pair of (partial) trees and each choice of argmin sets that it
discards by a linear program has a certificate accepted by `Farkas.check`, so by Lemma 4.6 (`L6.Farkas.check_sound`,
`check_sound_strict`, proved in `L6Sound/Common/Farkas.lean`; the composition with `decideLP_discard` is
`L6.F2.discard_no_solution` in `L6Sound/Composed.lean`) its system has no solution with `s > 0`; no prune of the
floating-point solver lacked a certificate; every listed cell has an exact point, hence is nonempty and meets
`ℓ(x) ≤ 0`; and the numbers of linear programs and prunes agree with the engine's run part by part. The parts repeat
the first two insertions; the Lean search is deterministic, so all parts take the same decisions there, and the
depth-3 counter assigns each depth-3 node to exactly one part.

**What it assumes (stated, not formalized in v1).** That the rows of `base_lp`, `threshold_row` and the argmin rows
are the conditions of Lemma 4.3 and Definition 4.4 (exponents as linear forms in the heights, (O1)/(O2), circles,
strict increase along the trees, root heights ≥ −2, argmin sets), that the relaxation of ℓ(x) ≤ 0 for pairs not yet
placed is valid, that the four combinatorial cuts are justified, and that restricting two trees to the points
inserted so far gives a node of the search: the framework of the proof of Proposition 4.5. Not re-checked: the split
of the engine's certificates into dual solutions / dual rays / exact simplex and the slacks of Table 2 (properties of
the Python run).

## Timings (box with 384 vCPUs, nice 10)

* Final run (`logs/f2/build_final.log`, `logs/f2/modules.tsv`): 29 min 42 s wall clock, 22,370 s user time (6.2
  CPU-hours); the longest module is class 3, part 358 (9,934,314 linear programs): 1,769 s; the next are parts 229
  (1,753 s) and 178 (1,743 s); the light class 0 (828,970 programs) takes 133 s. 0.16–0.18 ms per linear program
  (float simplex, exact recovery and check of every prune, row construction).
* Two earlier full runs with the same results for all 430 chunk and class modules: without the exact points and the
  per-part counters (`logs/f2/build_baseline_noleaf.log`, 22,945 s, longest 1,760 s) and with the exact points
  (`logs/f2/build_confirm_leaf.log`, 22,342 s, longest 1,758 s); both failed only in `All.lean` (a tactic typo,
  fixed). The engine's Python replay took 18.6 CPU-hours for the same searches.

## Rebuild

From the package root, after `lake exe cache get`: `python3 scripts/f2/gen_checks.py` (deterministic; writes the
modules of `L6Check/F2/` from `data/cells/`), then `lake build L6Check.F2.Axioms` (about 30 minutes on 384 cores;
`lake` runs the modules in parallel; the largest resident set of a process in the final run was 1.4 GB). Summaries:
`python3 scripts/f2/summarize.py <lake log> logs/f2`.
